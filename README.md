# TaskDigest

Портфолио-проект для учёта времени, потраченного на задачи в проектах. Пользователь формулирует задачу, отмечает начало и конец работы над ней (сессии), а любой посетитель сайта может посмотреть публичную статистику: какие у пользователя есть проекты, сколько времени потрачено на каждый и какие задачи в них решались.

Проект построен на **Nuxt 3** (Vue 3 + TypeScript), серверная часть работает на **Nitro**, хостинг и база данных — **Netlify**. Вход выполняется через **Google OAuth 2**, а сессиями работы можно управлять и из веб-интерфейса, и из **Telegram-бота**.

Проект ведётся по принципу **CODE-first**: источник истины — код. Полноценную документацию заранее не пишем, но сам код описан (JSDoc у всех функций и переменных), а утилиты и composables сопровождаются парными `.md`-файлами и тестами.

## Описание проекта

**TaskDigest** помогает вести учёт рабочего времени по проектам и задачам и показывать результат публично.

- Основной пользователь (владелец) регистрируется и входит через Google OAuth 2. Могут регистрироваться и другие пользователи: каждый работает **только со своими** проектами, задачами и сессиями.
- У пользователя несколько проектов. К проекту формулируется задача. Над задачей работают **сессиями**: фиксируется момент начала и момент окончания. Одну задачу можно решать за несколько сессий.
- Публичная часть доступна всем (зарегистрированным и нет) и работает **только на чтение**:
  - статистика пользователя: его проекты и суммарное время по каждому;
  - страница проекта: задачи, которые на нём выполнялись.
- Сессиями управляют двумя способами: через **веб-интерфейс** и через **Telegram-бот** (выбрать проект, выбрать задачу, начать сессию, завершить открытую сессию).
- Все проекты и задачи любого пользователя публичны, признака приватности нет. Служебные данные (email, идентификаторы Google и Telegram, токены) наружу не отдаются.

## Как это работает

### Сессии работы

- **Начало сессии.** Время начала проставляет сервер. Если у пользователя уже есть другая открытая сессия, он получает предупреждение (какой проект, какая задача, с какого времени). Это уведомление, а не запрет: несколько открытых сессий разрешены.
- **Завершение сессий.** Действие «Завершить открытую сессию» универсально: пользователь не выбирает конкретную сессию. Сервер находит **все открытые сессии этого пользователя** и закрывает только их. Одна и та же логика работает в веб-интерфейсе и в Telegram-боте.
- **Без правок задним числом.** Время начала и конца всегда ставит сервер. Редактировать закрытые сессии и создавать сессии с произвольным временем нельзя.

### Публичная статистика

- В суммарное время попадают только **завершённые** сессии.
- Проекты, у которых есть незавершённые сессии, обозначаются особо, а к общему времени такого проекта добавляется знак «+» (например, «12 ч 30 мин+»). Для скринридеров знак дополняется скрытым текстом.
- Подробности открытых сессий (какая задача, с какого времени) публично не показываются.

## Стек технологий

### Основные технологии

- **[Nuxt 3](https://nuxt.com/)** — фреймворк на базе Vue 3 с серверной частью (Nitro).
- **[Vue 3](https://vuejs.org/)** — Composition API, `<script setup lang="ts">`.
- **[TypeScript](https://www.typescriptlang.org/)** — статическая типизация.
- **[Netlify](https://www.netlify.com/)** — хостинг, serverless-функции, управляемая база данных **Netlify DB** (PostgreSQL).

### Интеграции

- **[Google OAuth 2](https://developers.google.com/identity/protocols/oauth2)** — вход пользователей.
- **[Telegram Bot API](https://core.telegram.org/bots/api)** — управление сессиями из мессенджера (через webhook).

### Инструменты

- **[Tailwind CSS](https://tailwindcss.com/)** — используется по особой схеме вместе с БЭМ (см. [Вёрстка, стили и доступность](#вёрстка-стили-и-доступность)).
- **[Vitest](https://vitest.dev/)** — модульное тестирование.
- **[Bun](https://bun.sh/)** — менеджер пакетов и запуск скриптов.
- **Prettier и ESLint** — запланированы (см. [дорожную карту](#статус-и-дорожная-карта)).

Конкретные пакеты для авторизации, доступа к БД и клиента Telegram пока не выбраны: их подбирает и устанавливает владелец проекта.

## Установка и запуск

Актуальный список команд — раздел `scripts` в `package.json`. Обычно:

```bash
git clone <repository-url>
cd <project-name>
bun install        # установка зависимостей
bun run dev        # dev-сервер Nuxt (обычно http://localhost:3000)
bun run build      # production-сборка
bun run preview    # локальный просмотр собранного приложения
bun run test       # тесты Vitest (когда подключены)
```

Команды с `npm run ...` работают так же, если вы не используете Bun.

> **`bun test` и `bun run test` — разные команды.** Первая запускает встроенный тест-раннер Bun и игнорирует конфигурацию Vitest. Нужна вторая: она запускает скрипт `test` из `package.json`.

Для работы авторизации, базы данных и бота перед запуском нужно задать переменные окружения (см. [Переменные окружения](#переменные-окружения)).

## Архитектура приложения

Придерживаемся разделения ответственности:

- **Pages / Layouts** отвечают за отображение страниц.
- **Components** содержат переиспользуемые элементы интерфейса.
- **Composables** инкапсулируют повторно используемую реактивную логику.
- **Server API** (`server/api/v1/`) — тонкие обработчики: разбор запроса, проверка доступа, вызов бизнес-логики, формирование ответа.
- **Server utils** (`server/utils/`) — бизнес-логика (старт и завершение сессий, подсчёт времени). Её используют и веб-API, и Telegram-бот, поэтому она не дублируется.
- **Types** содержат общие определения типов (клиент и сервер используют одни и те же).
- **Tests** (`*.spec.ts` рядом с кодом) проверяют поведение функций и компонентов.

Такое разделение снижает связанность модулей и упрощает развитие проекта.

## Модель данных

| Сущность        | Смысл                                                                              |
| --------------- | ---------------------------------------------------------------------------------- |
| **User**        | Пользователь (вход через Google). Владеет проектами. К нему привязывается Telegram |
| **Project**     | Проект пользователя. Время проекта — сумма времени всех сессий его задач           |
| **Task**        | Задача проекта: формулировка и признак «решена»                                    |
| **WorkSession** | Период работы над задачей: `startedAt` и `endedAt` (пока работа идёт — пусто)      |

Конкретные поля описаны в `types/` и схеме базы данных. Время хранится и передаётся в UTC (ISO 8601). Суммарное время проекта вычисляется как агрегат по сессиям, а не хранится отдельным полем. Хранилище — Netlify DB (PostgreSQL).

## Авторизация

- Вход выполняется через Google OAuth 2, пользователь определяется на сервере по серверной сессии (`httpOnly`-cookie).
- Все проверки доступа выполняются на сервере. Идентификатор пользователя берётся только из сессии, но не из тела запроса.
- Любая операция над проектом, задачей или сессией проверяет, что ресурс принадлежит текущему пользователю.
- Публичные эндпоинты не требуют входа и отдают только явно перечисленные безопасные поля.

Настройка OAuth-клиента в Google Cloud Console:

1. Создайте OAuth-клиент типа «Веб-приложение».
2. Добавьте разрешённые redirect URI для каждого окружения: локальная разработка, production и (при необходимости) deploy preview.
3. Передайте идентификатор и секрет клиента приложению через переменные окружения.

## API

Все эндпоинты находятся в `server/api/v1/` и доступны по адресу `/api/v1/...`. Версия в пути оставляет возможность выпустить несовместимые изменения как `v2`, не ломая `v1`.

- **Публичные** эндпоинты — только `GET`, без авторизации, возвращают только разрешённые поля (статистика пользователя, страница проекта).
- **Приватные** эндпоинты требуют входа: управление проектами, задачами и сессиями.
- Ошибки возвращаются стандартным способом Nitro (`createError`), входные данные валидируются на сервере.

Список эндпоинтов и контракты описаны в коде (`server/api/v1/**`, комментарии над обработчиками).

## Telegram-бот

Бот — второй способ управлять сессиями (первый — веб-интерфейс):

- сценарий: выбор проекта → выбор задачи → «Начать сессию»;
- универсальное действие «Завершить открытую сессию» доступно и кнопкой в главном меню, и слэш-командой; работает в один шаг из любого состояния диалога и закрывает все открытые сессии пользователя;
- при старте новой сессии бот предупреждает, если другая ещё открыта.

Как это устроено:

- Сервер работает на serverless Netlify, поэтому бот получает обновления через **webhook**, а не через long polling.
- Запрос на webhook проверяется по секретному токену (заголовок `X-Telegram-Bot-Api-Secret-Token`).
- Бот отвечает только Telegram-аккаунтам, привязанным к пользователю (проверка по числовому идентификатору, не по `@username`).
- Логика сессий общая с веб-API, повторная доставка одного и того же обновления не создаёт вторую сессию.

Регистрация webhook выполняется вручную владельцем:

```bash
curl "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
  --data-urlencode "url=<адрес эндпоинта webhook на вашем сайте>" \
  --data-urlencode "secret_token=<секретный токен>"
```

Подставьте реальные значения, не коммитьте токены в репозиторий.

## Вёрстка, стили и доступность

### БЭМ + Tailwind CSS

- Вся разметка пишется по методологии [БЭМ](https://getbem.com/naming/): `block`, `block__element`, `block--modifier`. Имена — в kebab-case, имя блока совпадает с именем компонента (`ProjectCard.vue` → `.project-card`).
- В HTML **нет утилитарных классов Tailwind**. Они применяются только в CSS-файлах к БЭМ-классам через `@apply`:

  ```css
  .project-card__title {
    @apply text-xl font-bold md:text-2xl;
  }
  ```

- В компонентах **нет блока `<style>`** (ни обычного, ни `scoped`, ни `module`). Для каждого БЭМ-блока заведён файл `assets/styles/components/<имя-блока>.css`.
- `assets/styles/style.css` — единая точка входа: в нём только `@import` (сначала Tailwind, затем тема и общие файлы, затем компоненты). Новый блок = новый css-файл + строка `@import`.
- Общие значения (цвета, шрифты, брейкпоинты) живут в `theme.css`: это основа для будущей тёмной темы.

### Доступность (ARIA)

- Сначала семантический HTML (`<button>`, `<nav>`, `<main>`, заголовки по порядку), ARIA — там, где семантики не хватает.
- У кнопок-иконок есть доступное имя (`aria-label`), декоративные элементы скрыты от скринридеров.
- Динамические сообщения (например, предупреждение об открытой сессии) объявляются через live-регионы (`role="status"`, `role="alert"`).
- Состояния отражаются ARIA-атрибутами (`aria-expanded`, `aria-current` и другие) и дублируются БЭМ-модификаторами.
- Смысл не передаётся только цветом или символом: знак «+» у времени проекта сопровождается текстом для скринридеров.
- Всё доступно с клавиатуры, видимый фокус не убирается.

## Тестирование

Для тестов используется **Vitest**. Тесты лежат рядом с проверяемым кодом: `*.spec.ts`.

- Каждая функция покрывается тестами сразу при создании: **позитивными** (корректное поведение) и **негативными** (некорректные данные, граничные значения, ошибки зависимостей, доступ к чужому ресурсу, неавторизованный вызов).
- Внешние сервисы (БД, Google, Telegram) в тестах заменяются моками.
- Названия тестов и комментарии — на русском.
- Компоненты с логикой проверяются через `@vue/test-utils`, селекторы строятся по БЭМ-классам; для интерактивных компонентов проверяются и ARIA-атрибуты.

```bash
bun run test           # watch-режим
bun run test --run     # разовый прогон (перед коммитом, в CI)
```

Vitest и вспомогательные пакеты подключаются владельцем проекта; до этого момента тесты можно писать, но запустить их не получится.

## Документация в коде

Описание нужно не только там, где «неочевидно»: сегодня код понятен, а через полгода — нет.

- Каждая функция, переменная и константа уровня модуля, тип и его поля, пропсы и эндпоинты описываются в формате JSDoc/TSDoc **на русском** (`@param`, `@returns`, `@throws`, при необходимости `@example`). Типы в JSDoc не дублируются.
- Для утилит (`utils/`, `server/utils/`) и composables рядом с кодом лежит парный `.md`: обзор, функции с сигнатурами, ошибки, ограничения. Для компонентов отдельные `.md` не нужны.
- При изменении поведения модуля обновляются его описание, `.md` и тесты.
- README и общую документацию не переписываем заранее: фиксируем только то, что уже есть в коде.

## Переменные окружения

Секреты и настройки задаются переменными окружения. Файл `.env` не коммитится, значения для production задаются в настройках Netlify. Точный список имён определяется кодом (`runtimeConfig` в `nuxt.config.ts`).

| Назначение                             | Где задаётся                         | Доступно браузеру |
| -------------------------------------- | ------------------------------------ | ----------------- |
| Идентификатор и секрет Google OAuth    | `.env` локально, Netlify на хостинге | Нет               |
| Ключ шифрования серверной сессии       | `.env` локально, Netlify на хостинге | Нет               |
| Подключение к базе данных (Netlify DB) | Netlify / Netlify CLI                | Нет               |
| Токен Telegram-бота и секрет webhook   | `.env` локально, Netlify на хостинге | Нет               |

Значения `runtimeConfig` на хостинге переопределяются переменными вида `NUXT_<КЛЮЧ>` (для публичных — `NUXT_PUBLIC_<КЛЮЧ>`). Секреты никогда не кладутся в `runtimeConfig.public` и не попадают в клиентский код.

## Деплой на Netlify

Серверная часть выполняется как serverless-функции. Схема работы:

1. Подключите репозиторий к Netlify (Add new site → Import an existing project).
2. Netlify обычно сам определяет Nuxt и запускает сборку; Nitro выбирает подходящий пресет автоматически. Если автоопределение не сработало, укажите команду сборки `bun run build`.
3. Задайте переменные окружения в настройках сайта (Site configuration → Environment variables).
4. Подключите Netlify DB по [документации Netlify](https://docs.netlify.com/) (способ подключения и пакеты менялись, сверяйтесь с актуальной документацией).
5. Добавьте адрес сайта в разрешённые redirect URI OAuth-клиента Google.
6. Зарегистрируйте webhook Telegram-бота на адрес сайта (см. [Telegram-бот](#telegram-бот)).

Подробнее о развёртывании Nuxt на Netlify: [nuxt.com/deploy/netlify](https://nuxt.com/deploy/netlify).

### Особенности serverless

- Нет постоянной файловой системы для записи и общего состояния в памяти между запросами: любое состояние хранится в БД.
- У функций есть лимит времени выполнения: эндпоинты должны быть короткими, агрегации выполняются запросами к БД.
- Локальный `.env` на хостинг не попадает: переменные нужно задать в Netlify отдельно.
- Deploy preview имеет отдельный адрес, поэтому для него нужен свой redirect URI в Google Cloud Console.

### Возможные проблемы

| Симптом                                               | Вероятная причина                                              | Что делать                                                                 |
| ----------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Ошибка `redirect_uri_mismatch` при входе через Google | Адрес возврата не добавлен в OAuth-клиент                      | Добавить точный URI (с учётом схемы, домена и пути) в Google Cloud Console |
| API работает локально, но падает на Netlify           | На хостинге не заданы переменные окружения                     | Проверить переменные в настройках сайта Netlify                            |
| Бот не отвечает                                       | Webhook не зарегистрирован, неверный адрес или секретный токен | Проверить регистрацию webhook и значение секретного токена                 |
| В deploy preview не видно данных из production        | Preview может работать с отдельной веткой БД                   | Проверить настройки Netlify DB для превью                                  |
| Состояние «теряется» между запросами                  | Данные хранятся в памяти serverless-функции                    | Хранить состояние в БД                                                     |

## Рекомендации по разработке

Подробные правила — в [`AGENTS.md`](AGENTS.md). Кратко:

- **TypeScript:** строгая типизация, без `any`; общие типы — в `types/` и импорт через `import type`.
- **Vue:** Composition API, `<script setup lang="ts">`, бизнес-логика отдельно от представления.
- **Сервер:** эндпоинты тонкие, логика — в `server/utils/`; публичные эндпоинты отдают только разрешённые поля.
- **Безопасность:** пользовательские строки считаются недоверенными, `v-html` с ними не используется; секреты — только в переменных окружения.
- **Время:** UTC в хранилище и API, локальное время — только в интерфейсе.
- **Форматирование:** пока Prettier не подключён, код пишется в его стиле по умолчанию (двойные кавычки, точки с запятой, 2 пробела, ширина 80).
- **Зависимости:** добавляются только владельцем проекта вручную.

## Работа с AI-агентами

Правила для AI-агентов, работающих с репозиторием, находятся в файле [`AGENTS.md`](AGENTS.md). Главное из них:

- агент делает только то, о чём его просят, и не расширяет задачу по собственной инициативе;
- агент не устанавливает пакеты и зависимости, а сообщает владельцу, что именно нужно добавить и зачем;
- для каждой новой функции агент пишет описание, при необходимости парный `.md` и тесты (позитивные и негативные).
