# AGENTS.md

Инструкции для AI-агентов, работающих с этим репозиторием. Здесь только то, что нужно для безопасных и совместимых с кодовой базой изменений. Проект ведётся по принципу **CODE-first**: сначала код, полноценную проектную документацию заранее не пишем. Но сам код всегда описан: функции, переменные и типы имеют документирующие комментарии, а утилиты и composables — парные `.md`-файлы и тесты.

## Главные правила (читать первыми)

### 1. Работай только внутри папки проекта

**Наистрожайшее правило.** Агент запускается исключительно в папке проекта, и любые
действия за её пределами запрещены.

- Читать, искать, просматривать каталоги, править файлы и запускать команды разрешено
  **только внутри папки проекта** — её корнем считается текущий рабочий каталог.
- **Запрещено** выходить за пределы папки: в домашний каталог, родительские каталоги,
  соседние проекты, системные и прикладные директории. Нельзя даже «просто посмотреть»,
  что там лежит.
- Не используй абсолютные пути, ведущие наружу, не запускай команды с рабочим каталогом
  вне проекта и не создавай за его пределами файлы, включая временные.
- Если задача, кажется, требует доступа наружу — **остановись и спроси владельца**. Без его
  явного разрешения на конкретный путь ничего за пределами проекта не делай.

### 2. Делай только то, о чём просят

- Решай ровно ту задачу, которая сформулирована в запросе. Не расширяй её, не «улучшай заодно», не реализуй фичи «на будущее».
- Не рефакторь, не переименовывай и не переформатируй код, который не относится к задаче.
- Не создавай файлы, абстракции, хелперы, конфиги и слои «про запас». Минимальное решение, которое работает, лучше универсального.
- Если запрос неоднозначен — задай один короткий уточняющий вопрос. Если вопрос не нужен, выбери самую узкую трактовку и в конце ответа одной строкой скажи, что именно ты предположил.
- Заметил проблему вне задачи (баг, уязвимость, устаревший код) — **сообщи о ней в ответе, но не исправляй** без явной просьбы.
- Не меняй архитектурные решения, структуру каталогов, настройки деплоя и конфигурацию сборки, если об этом не просили.
- **Исключение, не считающееся расширением задачи:** описания, парные `.md` и тесты для функций, которые ты создаёшь или меняешь, — обязательная часть самой задачи (см. разделы «Документирование кода», «Документация модулей» и «Тестирование»).

### 3. Зависимости и пакеты — только вручную владельцем

Без явного разрешения **запрещено**:

- запускать `bun add`, `npm install <пакет>`, `pnpm add`, `nuxi module add` и любые аналоги;
- править секции `dependencies` / `devDependencies` в `package.json`;
- менять lock-файл (`bun.lock` и т. п.) и список `modules` в `nuxt.config.ts` ради нового модуля;
- подключать сторонние скрипты, шрифты или стили через CDN/`<script>`/`<link>`.

Если для задачи нужен пакет (Nuxt-модуль, библиотека авторизации, драйвер БД, ORM, клиент Telegram, тестовая утилита и т. д.):

1. **Остановись** и не пытайся обойти ограничение «кривым» самописным решением, если оно заметно хуже.
2. Напиши владельцу: название пакета, зачем он нужен, есть ли вариант без него, и точную команду установки.
3. Реализуй ту часть задачи, которая не зависит от пакета, либо дождись ответа.

Команда `bun install` (установка того, что уже описано в `package.json`) допустима.

### 4. CODE-first: ничего не пишем заранее, но существующий код описываем

- Не пишите проектную документацию заранее: никаких спецификаций, ADR, планов и схем «на будущее» в `docs/`.
- Документация описывает **уже существующий** код: появилась функция — сразу появилось её описание (и, для утилит и composables, парный `.md` и тесты).
- README не переписывайте целиком и не дополняйте без просьбы; правьте в нём только то, что затронуто вашим изменением.

## Что за проект

**TaskDigest** — портфолио-проект: учёт времени, потраченного на задачи в проектах.

- Основной пользователь — владелец репозитория. Регистрируется и входит через **Google OAuth 2**. Возможна регистрация других пользователей: каждый работает **только со своими** проектами, задачами и сессиями.
- У пользователя есть несколько проектов. К проекту формулируется задача. Над задачей работают **сессиями**: фиксируется время начала и окончания работы. Одну задачу можно решать за несколько сессий.
- Публичная часть (доступна и незарегистрированным, и зарегистрированным пользователям, **только чтение**): статистика пользователя — список его проектов и суммарное время по каждому (учитываются только завершённые сессии, см. «Правила учёта времени»); страница проекта — задачи проекта.
- Сессиями пользователь управляет двумя способами: через **веб-интерфейс** и через **Telegram-бот** (после привязки аккаунта). В обоих каналах доступны одни и те же действия: выбрать проект, выбрать задачу, начать новую сессию, завершить открытую сессию.

### Предметная область

| Сущность        | Смысл                                                                               |
| --------------- | ----------------------------------------------------------------------------------- |
| **User**        | Пользователь (вход через Google). Владеет проектами. К нему привязывается Telegram. |
| **Project**     | Проект пользователя. Время проекта = сумма времени всех сессий всех его задач.      |
| **Task**        | Задача проекта: формулировка, признак «решена». Принадлежит одному проекту.         |
| **WorkSession** | Период работы над задачей: `startedAt`, `endedAt` (пока работа идёт — пусто).       |

Конкретные поля и их типы определяются в коде (`types/`) и схеме БД — не выдумывайте их заранее, добавляйте по мере реальной необходимости задачи.

### Правила учёта времени (приняты, не пересматривать)

- У пользователя **может быть несколько открытых сессий одновременно** — запрета нет.
- При начале новой сессии, если у пользователя уже есть другая открытая, ответ **обязан содержать предупреждение**: какая сессия ещё открыта (проект, задача, время начала). Это уведомление, а не блокировка: новая сессия создаётся. Логика одна и та же для веб-API и Telegram-бота.
- **Никакого редактирования сессий задним числом.** Время начала и окончания всегда проставляет сервер (текущий момент); клиент и бот эти значения не передают. Эндпоинтов, меняющих `startedAt`/`endedAt` у существующих сессий, и ручного создания сессий с произвольным временем нет.
- **Завершение сессий.** Действие «Завершить открытую сессию» универсально: пользователь не выбирает, какую именно сессию закрыть. Сервер сам находит **все открытые сессии этого пользователя** и закрывает **только их** (сессии других пользователей и уже закрытые не затрагиваются). Логика одна для веб-интерфейса и бота. Если открытых сессий нет, действие ничего не меняет и не считается ошибкой.
- **Публичная статистика.** В суммарное время попадают только **завершённые** сессии. Проекты, у которых есть незавершённые сессии, обозначаются особо, а к общему времени такого проекта добавляется знак «+» (например, «12 ч 30 мин+»). Знак показывается везде, где выводится общее время проекта. Подробности открытых сессий (задача, время начала) публично не отдаются — достаточно признака на уровне проекта.

### Видимость данных

Все проекты и задачи любого пользователя **публичны**, признака приватности нет. Это не относится к служебным данным: email, идентификатор Google, Telegram-идентификаторы, токены и прочие внутренние поля наружу не отдаются никогда.

## Планируемые возможности

Эти возможности запланированы (интернационализация, тёмная тема и настройка форматирования/линтинга — одними из первых), но **реализуются только по явной просьбе** — не добавляйте их по собственной инициативе:

- интернационализация (i18n);
- тёмная тема;
- форматирование и линтинг (Prettier и ESLint);
- Telegram-бот (описание требований — в разделе «Telegram-бот»).

Когда для этого понадобятся пакеты (Nuxt-модуль для i18n, Prettier, ESLint и т. д.), действует правило №3: сообщить владельцу, а не ставить самому.

## Стек

- **Nuxt 3** (Vue 3, Composition API, `<script setup lang="ts">`), **TypeScript**.
- Серверная часть — **Nitro** (`server/` внутри Nuxt), деплой на **Netlify**.
- База данных — **Netlify DB** (управляемый PostgreSQL), см. «База данных».
- Авторизация — Google OAuth 2 + серверные сессии (конкретный пакет не выбран).
- Стили — **Tailwind CSS** по особой схеме вместе с БЭМ (см. «Вёрстка и стили»).
- Тесты — **Vitest** (см. «Тестирование»).
- Пакетный менеджер: **Bun**. Если lock-файл в репозитории другой — следуйте ему.

## Команды

Источник истины — раздел `scripts` в `package.json`. Обычно:

```bash
bun install        # установка зависимостей из package.json
bun run dev        # dev-сервер Nuxt
bun run build      # production-сборка (Nitro preset для Netlify)
bun run preview    # локальный просмотр собранного приложения
bun run test --run # разовый прогон тестов (когда Vitest подключён)
```

Проверка изменений: `bun run build`, а также линтер/проверка типов, если они есть в `package.json`, и тесты затронутых модулей. Перед завершением задачи — полный прогон тестов. Не добавляйте новые скрипты и инструменты ради проверки.

## Структура

Ориентируйтесь на фактическое дерево репозитория. Базовая раскладка Nuxt 3, которой следуем:

```text
pages/            # маршруты (файловый роутинг)
layouts/          # шаблоны страниц
components/       # переиспользуемые компоненты (автоимпорт)
composables/      # useXxx-функции (автоимпорт) + парные *.md и *.spec.ts
utils/            # чистые клиентские/общие утилиты (автоимпорт) + парные *.md и *.spec.ts
assets/
└── styles/       # все стили проекта (БЭМ + Tailwind CSS)
    ├── style.css       # единая точка входа: только @import других css-файлов
    ├── components/     # по одному css-файлу на БЭМ-блок
    └── ...             # theme.css и прочие общие файлы
types/            # типы, используемые более чем в одном файле
server/
├── api/
│   └── v1/       # HTTP-эндпоинты Nitro, версия 1
└── utils/        # серверная логика и хелперы + парные *.md и *.spec.ts
public/           # статика
nuxt.config.ts
```

Каталоги создавайте по мере необходимости, а не заранее. Если расположение иное в самом репозитории (например, каталог `app/` из Nuxt 4) — следуйте ему.

## Соглашения кода

- **Язык:** комментарии, JSDoc, названия тестов и сообщения коммитов — на русском. Идентификаторы — на английском.
- **TypeScript:** строгая типизация. `any` не используйте — берите `unknown` и сужайте типы. Неиспользуемые переменные и параметры не оставляйте.
- **Компоненты:** `<script setup lang="ts">`, Composition API. Один компонент — одна ответственность.
- **Автоимпорт Nuxt** (компоненты, composables, `utils/`) использовать можно, но типы импортируйте явно.
- **Форматирование и линтинг:** Prettier и ESLint ещё не подключены (они запланированы, см. «Планируемые возможности»). Пока их нет, не добавляйте их и не создавайте их конфигурацию, а код пишите в стиле Prettier по умолчанию: двойные кавычки, точки с запятой, отступ 2 пробела, ширина строки 80. Когда конфигурация появится — следуйте ей.
- **Отладка:** `console.log` не оставляйте. `console.warn`/`console.error` — только при обработке ошибок.
- **Не редактируйте** вручную `.nuxt/`, `.output/`, `dist/`, `node_modules/`, lock-файл.

### Документирование кода

Описание нужно не только там, где «неочевидно»: сегодня код понятен, а через полгода — уже нет. Поэтому **описывается всё**. Используйте стандартный JSDoc/TSDoc на русском.

Обязательно описываются:

- каждая функция (экспортируемая, внутренняя, стрелочная в `const`): назначение, `@param`, `@returns`, `@throws` (если бросает), `@example` — когда он помогает понять использование;
- каждая переменная и константа уровня модуля, а также реактивное состояние (`ref`, `reactive`, `computed`) на уровне модуля и composable;
- каждый тип, интерфейс и **каждое его поле**; пропсы и события компонентов;
- эндпоинты `server/api/v1/**`: что делает, кто имеет доступ (публичный/приватный), параметры, формат ответа, возможные ошибки.

Правила качества описаний:

- Объясняйте **назначение и контракт** (зачем, какие допущения, граничные случаи, единицы измерения, что бывает при ошибке), а не пересказывайте код словами. Комментарий «увеличивает счётчик» бесполезен.
- Типы в JSDoc не дублируйте (`{string}` не нужен) — их задаёт TypeScript.
- Локальные переменные внутри тела функции описывайте, только если их смысл неочевиден (магические значения, неочевидный порядок действий, обход ограничения).
- Описание устаревает вместе с кодом: меняя поведение, обновляйте и комментарий.

**Существующие файлы.** Когда вы меняете файл, описывайте всё, что создаёте или меняете. Если в этом же файле есть функции, переменные или типы без описаний — допишите описания (код не трогайте). Массовое документирование файлов, к которым задача не относится, — только по просьбе.

### Типы (`types/`)

- Все типы, интерфейсы и псевдонимы, которые используются **более чем в одном файле** (в том числе клиентом и сервером), хранятся в `types/` в формате TypeScript (`*.ts`).
- Тип, нужный только одному файлу (например, `Props` компонента), остаётся в этом файле. Как только появляется второй потребитель — переносите тип в `types/`.
- Файлы группируйте по предметной области: `types/project.ts`, `types/task.ts`, `types/session.ts`, `types/api.ts`. Не складывайте всё в один файл.
- Импортируйте явно и с ключевым словом `type`: `import type { Project } from "~/types/project";`.
- Не дублируйте типы. В `types/` — только объявления типов, без runtime-кода.

### Документация модулей (`*.md`)

- Для **утилит** (`utils/`, `server/utils/`) и **composables** (`composables/`) рядом с файлом лежит парный `*.md` с тем же именем (`utils/formatDuration.ts` ↔ `utils/formatDuration.md`).
- Содержание: обзор (зачем модуль), список функций с сигнатурами и примерами, ошибки и исключения, ограничения и допущения.
- Для компонентов, страниц и эндпоинтов отдельные `.md` **не нужны** — их описывают комментарии в коде.
- **При изменении поведения модуля обновляйте его `.md`** и `*.spec.ts`. Новый модуль создаётся сразу с тремя файлами: код, `.md`, `.spec.ts`.
- README и общие `*.md` не переписывайте целиком — правьте только затронутое изменением.

### Тестирование (`*.spec.ts`)

- Тест-раннер — **Vitest**. Тесты лежат рядом с проверяемым кодом: `utils/<модуль>.spec.ts`, `composables/<имя>.spec.ts`, `server/utils/<модуль>.spec.ts`, `components/<Компонент>.spec.ts`.
- **Каждая создаваемая функция покрывается тестами** сразу при создании — и позитивными, и негативными:
  - позитивные: ожидаемое поведение на корректных данных;
  - негативные: некорректные и пустые входные данные, граничные значения, ошибки зависимостей, попытка доступа к чужому ресурсу, неавторизованный вызов.
- Тесты не обращаются к настоящим внешним сервисам: БД, Google, Telegram заменяются моками (`vi.mock`, `vi.fn`).
- Vue-компоненты с логикой (зависимость от пропсов, события, условный рендер) монтируются через `@vue/test-utils`. Селекторы строятся по БЭМ-классам (`.hero__title`), а не по утилитам Tailwind. Для интерактивных компонентов проверяйте и ARIA-атрибуты (`aria-label`, `aria-expanded`, роли live-регионов).
- Имена `describe`/`test` и комментарии в тестах — на русском.
- Если Vitest или его вспомогательные пакеты ещё не установлены, тесты всё равно пишутся, а в ответе вы сообщаете владельцу, какие пакеты нужно поставить, чтобы их запустить (правило №3).

### Вёрстка и стили (БЭМ + Tailwind CSS)

**БЭМ в разметке.**

- Весь HTML (шаблоны `*.vue`, `app.vue`, страницы, layouts) пишется по методологии **БЭМ**: `block`, `block__element`, `block--modifier` / `block__element--modifier`.
- Имена — в нижнем регистре через дефис (kebab-case): `session-list`, `session-list__item`, `session-list__item--active`.
- Блок — самостоятельная сущность, как правило соответствует компоненту, странице или layout; имя блока совпадает с именем в kebab-case (`ProjectCard.vue` → `.project-card`).
- Элемент принадлежит блоку и не существует вне него. Вложенность элементов в имени не отражается: `block__elem`, а **не** `block__elem__subelem`.
- Модификатор не используется без модифицируемого блока/элемента: пишем `class="hero__title hero__title--large"`, а не только `hero__title--large`.
- Стилизация только по классам: не используйте селекторы по тегам и `id`, а также глубокую вложенность.
- **`<style scoped>`, `<style module>` и `:deep()` не используются.** Изоляцию обеспечивают уникальные имена БЭМ.

**Tailwind CSS — только в CSS-файлах.**

- В HTML-разметке **запрещены** утилитарные классы Tailwind (`flex`, `p-4`, `text-lg`, ...). В атрибутах `class` пишутся только классы БЭМ.
- Утилиты Tailwind применяются внутри CSS-файлов к БЭМ-классам через `@apply`:

  ```css
  .hero__title {
    @apply text-3xl font-bold md:text-5xl;
  }

  .hero__title--large {
    @apply text-5xl;
  }
  ```

- Для каждого БЭМ-блока заведите отдельный файл `assets/styles/components/<имя-блока>.css`. В компонентах нет блока `<style>` вообще.
- Общие значения (цвета, шрифты, брейкпоинты) определяются в `assets/styles/theme.css`, а не «магическими числами» в файлах блоков: это основа для будущей тёмной темы.

**Структура `assets/styles/style.css`.**

`style.css` — единая точка входа стилей. В нём **только** `@import`: сначала Tailwind, затем варианты, тема, утилиты и базовые элементы, затем компоненты. Порядок важен — сохраняйте его.

- Новый блок — это новый файл в `assets/styles/components/` **и** строка `@import` в `style.css`. Файл, не подключённый в `style.css`, в сборку не попадает.
- Имя файла совпадает с именем БЭМ-блока.
- Не создавайте дополнительных точек входа и не импортируйте css-файлы блоков напрямую из компонентов. Подключение `style.css` в приложение — через `css` в `nuxt.config.ts`.
- Версию Tailwind и способ его подключения определяет репозиторий; сам Tailwind (пакет, модуль) вы не устанавливаете — правило №3.

**Доступность: ARIA для скринридеров.**

- Сначала семантический HTML, ARIA — только там, где семантики не хватает: `<button>` вместо `<div role="button">`, а также `<nav>`, `<main>`, `<header>`, `<footer>`, списки через `<ul>`/`<li>`, один `<h1>` на страницу и заголовки без пропуска уровней. Семантический тег не заменяет БЭМ-класс: класс остаётся.
- У интерактивного элемента без видимого текста (кнопка-иконка) есть доступное имя: `aria-label` или связь через `aria-labelledby`. Декоративные иконки скрываются от скринридеров (`aria-hidden="true"`), у декоративных `<img>` — пустой `alt=""`.
- У каждого поля формы есть `<label>`, связанный с полем. Ошибки валидации связываются с полем через `aria-describedby`, а само поле помечается `aria-invalid="true"`.
- Сообщения, появляющиеся без перезагрузки страницы, объявляются через live-регионы: `role="status"` для обычных и `role="alert"` для ошибок. Это относится, например, к предупреждению «другая сессия ещё открыта», результату завершения сессий и ошибкам запросов. Контейнер live-региона должен быть в DOM до появления текста.
- Состояние виджетов отражается ARIA-атрибутами: `aria-expanded` вместе с `aria-controls` у раскрывающихся блоков, `aria-current="page"` у активной ссылки навигации, `aria-busy="true"` во время загрузки, `aria-pressed` у переключателей. Состояние дублируется БЭМ-модификатором (`--active`, `--expanded`): стили вешаются на классы, а не на ARIA-атрибуты, поэтому атрибут и модификатор меняются вместе.
- Смысл не передаётся только цветом или символом. Знак «+» у общего времени проекта (есть незавершённые сессии) дополняется текстом для скринридеров, например `<span class="project-card__open-note">и ещё идёт работа</span>` со стилем `@apply sr-only` в CSS-файле блока, иначе «+» озвучится неинформативно.
- Всё доступно с клавиатуры: логичный порядок Tab, видимый фокус (не убирайте `outline` без замены), при закрытии модальных окон и меню фокус возвращается на вызвавший элемент.
- Тексты для скринридеров (`aria-label`, скрытые подсказки) — такие же пользовательские тексты, как и видимые: при внедрении i18n они переводятся наравне с ними.

## Ключевые архитектурные правила

### Авторизация и доступ

- Все проверки доступа выполняются **на сервере** (`server/`). Клиентские проверки — только для UX, не защита.
- Публичные эндпоинты — только чтение, без авторизации. Приватные (создание и изменение проектов, задач, сессий) требуют авторизованного пользователя.
- Идентификатор текущего пользователя берётся **только из серверной сессии** (для бота — из привязанного Telegram-аккаунта), никогда не из тела запроса, query или заголовков от клиента.
- Любая операция над проектом, задачей или сессией сначала проверяет, что ресурс принадлежит текущему пользователю. Чужой ресурс — `404` (или `403`), без утечки деталей.
- Сессия хранится на сервере/в `httpOnly`-cookie. Токены Google и сессии **не** кладутся в `localStorage` и не попадают в ответы API, логи и клиентский код.
- Не придумывайте собственную криптографию и самописный OAuth-протокол. Выбор пакета для авторизации — решение владельца (см. «Пока не решено»).

### API (`server/api/v1/`)

- Все эндпоинты лежат в `server/api/v1/` и доступны по адресу `/api/v1/...`. Префикс версии — прослойка для будущих несовместимых версий: ломающие изменения идут в новый каталог `v2/`, а контракт `v1` без явной просьбы не меняется.
- Публичные эндпоинты поддерживают только `GET` и возвращают **только явно перечисленные поля** (отдельный DTO), а не сырые записи БД.
- Ошибки — через `createError({ statusCode, statusMessage })`. Входные данные (body, query, params) валидируйте на сервере до использования.
- Эндпоинты тонкие: разбор запроса, проверка доступа, вызов функции из `server/utils/`, формирование ответа. Бизнес-логика (старт и завершение сессии, подсчёт времени) живёт в `server/utils/` и **используется и веб-API, и Telegram-ботом** — дублировать её в обработчиках нельзя.
- Типы ответов и запросов делятся между клиентом и сервером через `types/`.

### База данных

- Хранилище — **Netlify DB** (управляемый PostgreSQL). Подключение и миграции описаны в документации Netlify; она менялась (на сентябрь 2026 пакет `@netlify/database` заменил `@netlify/neon`, переменная `NETLIFY_DATABASE_URL` стала `NETLIFY_DB_URL`). Перед работой с БД сверяйтесь с актуальной документацией и не копируйте устаревшие туториалы.
- Драйвер, ORM и способ миграций выбирает владелец. Пакеты не устанавливайте (правило №3).
- Доступ к БД — только из `server/`. Параметры запросов всегда передаются как параметры, не конкатенацией строк (защита от SQL-инъекций).
- Каждый запрос на чтение или изменение пользовательских данных фильтруется по владельцу (`userId` из сессии).

### Telegram-бот

- Бот — один из двух каналов управления сессиями (второй — веб-интерфейс). Сценарий: выбор проекта → выбор задачи → «Начать сессию»; плюс универсальная кнопка «Завершить открытую сессию».
- Действие «Завершить открытую сессию» доступно в боте двумя способами: как кнопка в главном меню и как слэш-команда. Оно работает **в один шаг из любого состояния диалога** — не нужно сначала выбирать проект или задачу, чтобы пользователь не тратил время. Имя команды короткое, выбирается при реализации и описывается в коде.
- Это действие универсально: бот не спрашивает, какую сессию закрыть, и не принимает идентификатор сессии ни из кнопки, ни из команды. И кнопка, и команда вызывают одну и ту же общую серверную функцию, которая сама находит все открытые сессии этого пользователя и закрывает только их (см. «Правила учёта времени»).
- Сервер работает на serverless Netlify, поэтому бот принимает обновления через **webhook** (эндпоинт в `server/api/v1/`), а не через long polling.
- Запрос на webhook проверяется по секретному токену (заголовок `X-Telegram-Bot-Api-Secret-Token`, значение задано при регистрации webhook). Нет или неверный токен — отказ без обработки.
- Бот принимает команды **только от Telegram-аккаунтов, привязанных к пользователю**; определение — по числовому идентификатору отправителя, не по `@username`. Чужим пользователям бот не отвечает данными. Способ привязки аккаунта к пользователю — решение владельца.
- Обработка идемпотентна: Telegram может повторно доставить одно и то же обновление, и это не должно создавать вторую сессию.
- Отвечайте быстро (укладывайтесь в лимит serverless-функции) и всегда возвращайте `200`, если обновление принято, чтобы Telegram не слал его снова.
- В `callback_data` инлайн-кнопок — короткие идентификаторы: Telegram ограничивает её 64 байтами.
- Токен бота — только в переменной окружения. Регистрацию webhook и создание бота выполняет владелец, не агент.
- Логика сессий — общие функции из `server/utils/`, те же правила учёта времени (уведомление об открытой сессии, время только серверное).

### Время и статистика

- Моменты времени хранятся и передаются в UTC (ISO 8601); в локальное время переводит только интерфейс.
- Длительность считается из `startedAt`/`endedAt` на сервере. Суммарное время проекта — агрегат по сессиям, а не вручную поддерживаемое поле.
- Конец сессии не может быть раньше начала.
- Закрытая сессия неизменяема (см. «Правила учёта времени»).
- Публичная статистика считается только по завершённым сессиям (`endedAt` заполнено). Для проекта вычисляется признак наличия незавершённых сессий; он входит в публичный DTO, и по нему интерфейс обозначает проект особо и добавляет «+» к общему времени.

### Недоверенные строки

Названия проектов, формулировки задач и любые другие пользовательские строки показываются публично, поэтому считаются недоверенными:

- **Не используйте `v-html`** и `innerHTML` с пользовательскими данными. Вывод через шаблон Vue (`{{ }}`) экранируется автоматически.
- Длину и допустимое содержимое строк ограничивайте при записи на сервере.
- Строки, попадающие в `<title>`/meta-теги, нормализуйте (уберите управляющие и невидимые символы, ограничьте длину).
- Текст, приходящий из Telegram, проходит ту же валидацию, что и данные из веб-API.

### Секреты и конфигурация

- Секреты (Google client secret, ключ сессии, строка подключения к БД, токен Telegram-бота, секрет webhook) — только в переменных окружения. В репозиторий не коммитятся, в клиентский код не попадают, в логи не пишутся.
- Доступ к конфигурации — через `useRuntimeConfig()`. Приватные значения лежат в корне `runtimeConfig`, публичные — в `runtimeConfig.public` (и только если их безопасно показать браузеру).
- Значения `runtimeConfig` на хостинге переопределяются переменными окружения вида `NUXT_<КЛЮЧ>` (для публичных — `NUXT_PUBLIC_<КЛЮЧ>`). Реальные значения задаёт владелец в настройках Netlify.
- Файлы `.env*` с реальными секретами не создавайте и не коммитьте. Если нужна новая переменная — сообщите её имя и назначение владельцу, а не придумывайте значение.

## Подводные камни Netlify

- Серверная часть выполняется как **serverless-функции**: нет постоянной файловой системы для записи, нельзя хранить состояние в памяти между запросами, нет долгоживущих процессов и таймеров. Любое состояние — в БД.
- У функций есть лимит времени выполнения: эндпоинты должны быть короткими, агрегации выполняйте запросами к БД.
- Не меняйте `netlify.toml`, Nitro preset и настройки сборки без явной просьбы. Деплой идёт автоматически, публиковать вручную не нужно.
- Redirect URI для Google OAuth должен совпадать с реальным адресом приложения (production, deploy preview, локальный dev — разные адреса). Список разрешённых адресов настраивает владелец в Google Cloud Console — напишите ему, какой URI нужен.
- Переменные окружения задаются в Netlify отдельно: локальный `.env` на хостинг не попадает.
- Deploy preview может работать с отдельной веткой БД — не рассчитывайте, что данные production видны в превью.

## Чего не делать без явной просьбы

- Не добавляйте зависимости, модули, роутер-расширения, стейт-менеджер, UI-библиотеки, ORM (правило №3).
- Не реализуйте i18n, тёмную тему, форматирование/линтинг (Prettier, ESLint) и Telegram-бота, пока о них не попросили (раздел «Планируемые возможности»).
- Не добавляйте фичи, которых нет в описании проекта и в текущем запросе (роли, комментарии, уведомления, экспорт, графики, приватность проектов).
- Не создавайте проектную документацию заранее (правило №4).
- Не меняйте модель данных шире, чем требует текущая задача.
- Не добавляйте утилитарные классы Tailwind в разметку, не пишите правила в `style.css` (только `@import`), не добавляйте `<style>` в компоненты.
- Не трогайте настройки деплоя, Google OAuth-приложение, Telegram-бота и переменные окружения — только сообщайте, что нужно сделать владельцу.
