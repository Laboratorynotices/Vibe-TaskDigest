# Задача: Внедрение системы Spec Driven Development (SDD) и создание Agent Skill для управления жизненным циклом заданий

## 1. Цель задачи

Необходимо внедрить в существующий проект систему управления заданиями на основе принципов **Spec Driven Development (SDD)**.

Система должна обеспечить единый, предсказуемый и прозрачный процесс работы ИИ-агента с заданиями, описанными в отдельных Markdown-файлах.

Для этого необходимо:

1. Создать структуру директорий для хранения заданий с различными статусами и соответствующие README-файлы.
2. Создать новый Agent Skill `sdd-task-manager`, реализующий описанный ниже процесс работы с заданиями.
3. Обновить центральный `README.md` в корневой директории проекта.
4. Обновить `AGENTS.md` в корневой директории проекта, интегрировав в него правила использования новой системы.

**Важно:** задача заключается не просто в создании документации. Необходимо обеспечить согласованную работу всех трёх компонентов: структуры директорий, Agent Skill и центральных инструкций проекта.

---

## 2. Предварительный анализ проекта

До внесения изменений необходимо изучить существующий проект.

В частности:

- Определить текущую структуру директорий.
- Изучить корневой `README.md`.
- Изучить корневой `AGENTS.md`.
- Изучить существующую систему Agent Skills.
- Определить принятый в проекте формат и расположение Skills.
- Изучить правила оформления документации.
- Проверить существующие механизмы управления заданиями, если они имеются.
- Определить, каким образом инструкции и Skills подключаются и обнаруживаются используемыми ИИ-агентами.

На основании анализа необходимо определить оптимальное место для нового Skill и способ его интеграции.

Не создавать параллельные механизмы, если в проекте уже имеются подходящие решения.

Существующие правила и документацию необходимо сохранить. Не удалять и не переписывать несвязанные с задачей разделы.

Если обнаружены противоречия между существующими инструкциями и настоящим заданием, зафиксировать их и определить способ согласования. При наличии критических неоднозначностей перейти к процедуре уточнения требований.

## 3. Создание структуры директорий

В проекте необходимо создать следующую структуру:

```text
project/
│
├── docs/
│   └── tasks/
│       ├── README.md
│       │
│       ├── backlog/
│       │   └── README.md
│       │
│       ├── done/
│       │   └── README.md
│       │
│       ├── failed/
│       │   └── README.md
│       │
│       ├── questions/
│       │   └── README.md
│       │
│       └── [task files]
│
├── README.md
├── AGENTS.md
│
└── ...
```

Назначение директорий:

### `docs/tasks/backlog/`

Хранение заданий, которые запланированы на будущее, но ещё не готовы к выполнению или ожидают своей очереди.

ИИ-агент не должен самостоятельно выбирать задания из этой директории.

### `docs/tasks/`

Основная рабочая директория.

В ней непосредственно размещаются Markdown-файлы заданий, которые пользователь передал в работу.

ИИ-агент должен искать задания исключительно в этой директории.

### `docs/tasks/done/`

Хранение успешно выполненных заданий.

Задание может попасть сюда только после успешного прохождения всех обязательных проверок и подтверждения соответствия исходным требованиям.

### `docs/tasks/failed/`

Хранение заданий, выполнение которых завершилось неудачно либо обязательные проверки которых завершились с ошибками.

### `docs/tasks/questions/`

Хранение заданий, выполнение которых невозможно продолжить без дополнительной информации или решений пользователя.

### Требования к README-файлам

В каждой из пяти директорий необходимо создать `README.md`:

- `docs/tasks/README.md`
- `docs/tasks/backlog/README.md`
- `docs/tasks/done/README.md`
- `docs/tasks/failed/README.md`
- `docs/tasks/questions/README.md`

Файлы должны содержать краткое, но однозначное описание назначения соответствующей директории и правил работы с ней.

README-файлы также необходимы для сохранения пустых директорий в Git.

В README-файле директории `docs/tasks/` необходимо описать общую систему управления заданиями, их жизненный цикл и правила перехода между статусами.

## 4. Создание Agent Skill `sdd-task-manager`

Необходимо создать новый Agent Skill с названием:

`sdd-task-manager`

Skill должен содержать полную инструкцию для ИИ-агента по управлению жизненным циклом заданий.

Расположение и структура Skill должны соответствовать существующим соглашениям проекта и требованиям используемой платформы.

Необходимо проверить, что Skill оформлен в соответствии с поддерживаемым форматом и может быть обнаружен ИИ-агентом.

### 4.1. Основная ответственность Skill

Skill отвечает за:

1. Обнаружение заданий, переданных в работу.
2. Чтение и анализ требований.
3. Анализ архитектуры и существующего кода проекта.
4. Планирование реализации.
5. Выполнение задания.
6. Создание и обновление тестов.
7. Проверку результатов.
8. Формирование отчёта.
9. Определение итогового статуса.
10. Перемещение файла задания в соответствующую директорию.
11. Сохранение полной истории выполнения.

Skill не должен самостоятельно управлять приоритетами или выбирать задания из очереди `backlog`.

---

## 5. Жизненный цикл заданий

Основной процесс должен выглядеть следующим образом:

```text
                 backlog
                    |
                    | Пользователь выбирает задание
                    v
              docs/tasks/
                    |
                    | ИИ-агент выполняет задание
                    |
          +---------+---------+
          |         |         |
          v         v         v
         done     failed   questions
                              |
                              | Пользователь отвечает
                              | на вопросы
                              v
                         docs/tasks/
```

Пользователь самостоятельно перемещает файлы между директориями, определяя момент начала или повторного выполнения задания.

ИИ-агент отвечает за обработку заданий, находящихся непосредственно в `docs/tasks/`, и за перемещение завершённых файлов в соответствующие статусные директории.

### 5.1. Создание заданий

Новые задания создаются пользователем в:

`docs/tasks/backlog/`

Каждое задание представляет собой отдельный Markdown-файл.

Рекомендуемый формат имени:

`ID-short-task-name.md`

Примеры:

- `0008-add-user-authentication.md`
- `0009-refactor-database-layer.md`
- `0010-improve-error-handling.md`

Задание должно по возможности содержать:

- Цель.
- Описание требуемых изменений.
- Ожидаемый результат.
- Ограничения.
- Критерии приёмки.
- Условия успешного выполнения.

Если формулировка недостаточно ясная, пользователь может дополнить её до передачи в работу.

### 5.2. Передача задания в работу

Пользователь самостоятельно переносит выбранный файл из `backlog` непосредственно в:

`docs/tasks/`

После этого запускает ИИ-агента.

При запуске Skill агент должен:

1. Проверить содержимое `docs/tasks/`.
2. Найти все Markdown-файлы заданий, находящиеся непосредственно в этой директории.
3. Не учитывать README-файлы как задания.
4. Определить количество найденных заданий.
5. Прочитать каждое задание полностью.
6. Проанализировать требования.
7. Приступить к выполнению.

Если заданий несколько, агент должен выполнить их последовательно, не объединяя их в одну задачу и сохраняя отдельную историю для каждого файла.

**Ограничение области поиска:**

Агент не должен самостоятельно искать задания в:

- `docs/tasks/backlog/`
- `docs/tasks/done/`
- `docs/tasks/failed/`
- `docs/tasks/questions/`

Эти директории используются исключительно для хранения заданий с соответствующими статусами.

## 6. Процесс выполнения задания

### Шаг 1. Анализ проекта

Перед внесением изменений агент обязан:

- Изучить архитектуру проекта.
- Изучить связанные с заданием компоненты.
- Ознакомиться с существующими правилами разработки.
- Изучить существующие тесты.
- Определить потенциальные побочные эффекты.
- Установить используемые механизмы сборки, тестирования и статического анализа.

Необходимо учитывать существующие архитектурные решения и соглашения проекта.

### Шаг 2. Предварительная проверка состояния проекта

До внесения изменений необходимо выполнить доступные проверки проекта.

В первую очередь:

- Запустить существующие тесты.
- Проверить состояние сборки.
- Выполнить проверки типов, если они предусмотрены.
- Выполнить линтеры и статический анализ, если они используются.

Цель — зафиксировать состояние проекта до начала работы.

Это необходимо, чтобы отличать существовавшие ранее ошибки от ошибок, возникших вследствие реализации текущего задания.

Все обнаруженные исходные проблемы должны быть зафиксированы.

Если проверки невозможно выполнить, необходимо указать причину.

### Шаг 3. Планирование

Перед реализацией агент должен определить:

- Какие файлы потребуется изменить.
- Какие новые файлы необходимо создать.
- Какие компоненты будут затронуты.
- Какие тесты необходимо добавить или изменить.
- Какие потенциальные риски существуют.

Если обнаружены критические неоднозначности, без разрешения которых нельзя корректно выполнить задание, необходимо перейти к процедуре `questions`.

### Шаг 4. Реализация

Агент должен выполнить изменения в соответствии с исходными требованиями.

Обязательные ограничения:

- Не выходить за рамки задания без необходимости.
- Не удалять существующую функциональность без соответствующего основания.
- Не изменять несвязанные компоненты.
- Не нарушать существующую архитектуру.
- Соблюдать стандарты кодирования проекта.
- Не выполнять дополнительные задачи без разрешения пользователя.

Если в ходе реализации обнаружена необходимость дополнительных изменений, их следует зафиксировать в отчёте.

Агент может предлагать улучшения, но не должен реализовывать их без отдельного разрешения пользователя.

### Шаг 5. Подготовка тестов

Для новой функциональности необходимо подготовить соответствующие тесты.

Тесты должны охватывать:

- Основные сценарии использования.
- Граничные случаи.
- Возможные ошибки.
- Существенные побочные эффекты.

При необходимости необходимо обновить существующие тесты.

Запрещается удалять или ослаблять существующие тесты исключительно ради получения успешного результата.

### Шаг 6. Проверка результатов

После реализации необходимо выполнить:

1. Новые тесты.
2. Все существующие тесты.
3. Проверки типов.
4. Статический анализ.
5. Линтеры.
6. Сборку проекта, если она предусмотрена.

Необходимо использовать существующие механизмы проверки проекта.

Нельзя подменять полноценные проверки упрощёнными или выборочными проверками ради формального получения успешного результата.

Результаты необходимо сопоставить с результатами предварительной проверки.

При этом важно различать:

- Ошибки, существовавшие до начала работы.
- Ошибки, возникшие вследствие текущих изменений.
- Ошибки, которые невозможно однозначно классифицировать.

Если какие-либо проверки не удалось выполнить, это обязательно отражается в отчёте.

## 7. Формирование отчёта

После выполнения задания агент обязан дополнить исходный Markdown-файл отчётом.

**Исходное описание задания должно оставаться неизменным.**

Запрещается заменять первоначальные требования кратким пересказом выполненной работы.

Отчёт добавляется в конец файла.

Использовать следующую структуру:

```markdown
---

# Отчёт ИИ-агента

**Дата выполнения:** YYYY-MM-DD

## 1. Выполненные действия

Подробное описание выполненной работы.

Перечень созданных, изменённых и удалённых файлов.

Описание принятых архитектурных и технических решений.

## 2. Результаты тестирования

Какие тесты были запущены.

Какие тесты пройдены.

Какие тесты провалены.

Результаты проверок типов, линтеров,
статического анализа и сборки.

Какие проверки не проводились и почему.

Сравнение с состоянием проекта до начала работы.

## 3. Результат выполнения задания

Описание достигнутого результата.

Соответствие результата первоначальным требованиям.

Какие критерии приёмки выполнены.

Какие критерии не выполнены.

## 4. Комментарии

Дополнительные замечания.

Обнаруженные проблемы.

Особенности реализации.

Побочные эффекты.

## 5. Что ещё можно улучшить

Предложения по дальнейшему развитию,
оптимизации или улучшению решения.

Эти предложения не входят в текущее задание
и не должны реализовываться без отдельного разрешения.

## 6. Открытые вопросы

Вопросы, которые остались нерешёнными,
если таковые имеются.
```

При повторном выполнении задания новый отчёт добавляется после предыдущего с указанием даты.

Предыдущие отчёты нельзя удалять или переписывать.

---

## 8. Успешное выполнение — done

Файл задания разрешается переместить в:

`docs/tasks/done/`

только при одновременном выполнении следующих условий:

- Реализация соответствует исходным требованиям.
- Все новые тесты пройдены.
- Все существующие обязательные тесты пройдены.
- Все обязательные проверки завершились успешно.
- Результат соответствует критериям приёмки.
- В отчёте отражены выполненные действия и результаты проверок.

Если обязательные проверки не проводились или завершились неудачно, задание нельзя считать успешно выполненным.

Самостоятельное заявление агента об успешном выполнении не является достаточным основанием для перехода в `done`.

---

## 9. Недостаток информации — questions

Если выполнение невозможно из-за недостатка информации, противоречий в требованиях или критической неоднозначности, агент не должен самостоятельно придумывать недостающие требования.

Необходимо:

1. Зафиксировать недостающую информацию.
2. Объяснить, почему она необходима.
3. Сформулировать конкретные вопросы пользователю.
4. При необходимости предложить варианты решения.
5. Добавить вопросы в исходный файл задания.

Использовать формат:

```markdown
## Дополнительные вопросы

### Вопрос 1. Выбор способа авторизации

Какой способ авторизации необходимо использовать?

Варианты:

- OAuth 2.0.
- JWT.
- Существующая система авторизации проекта.

### Вопрос 2. Совместимость

Нужно ли сохранять совместимость со старым API?

Варианты:

- Да, полная обратная совместимость.
- Нет, допускается изменение API.
```

После этого файл перемещается в:

`docs/tasks/questions/`

Агент прекращает работу над данным заданием и сообщает пользователю о необходимости предоставить ответы.

### Возобновление работы

Пользователь самостоятельно:

1. Отвечает на вопросы непосредственно в файле.
2. Перемещает файл обратно в `docs/tasks/`.
3. Повторно запускает ИИ-агента.

При повторном запуске агент обязан прочитать весь файл, включая:

- Первоначальное описание.
- Предыдущие отчёты.
- Дополнительные вопросы.
- Ответы пользователя.

После этого выполнение продолжается с учётом полученных ответов.

Предыдущие отчёты не удаляются. Новый этап работы оформляется отдельным дополнением.

---

## 10. Неуспешное выполнение — failed

Если агент выполнил реализацию, но тесты или другие обязательные проверки завершились неудачно, файл задания необходимо переместить в:

`docs/tasks/failed/`

В отчёте обязательно указать:

- Какие тесты провалились.
- Какие проверки завершились ошибками.
- Какие компоненты или функции перестали работать.
- Какие ошибки обнаружены.
- Какие изменения могли привести к возникновению проблем.
- Какие тесты успешно пройдены.
- Какие проблемы существовали до начала работы.
- Что необходимо исправить для успешного завершения задания.

Особенно важно фиксировать случаи, когда новая функциональность реализована, но перестали работать ранее существовавшие возможности проекта.

Агент не должен выдавать частично работающую функциональность за успешно завершённую.

Перемещение задания в `failed` не запрещает повторное выполнение.

Пользователь может изучить отчёт, скорректировать требования или поручить устранение проблем.

Для повторной попытки пользователь самостоятельно возвращает файл в `docs/tasks/`.

---

## 11. Сохранение истории выполнения

Markdown-файл задания должен быть единственным источником истины относительно исходных требований и истории их реализации.

При повторном выполнении запрещается:

- Удалять первоначальное описание.
- Переписывать исходные требования без согласования.
- Удалять предыдущие отчёты.
- Удалять ответы пользователя.
- Удалять историю ошибок и проверок.

Все новые результаты добавляются в конец существующего файла.

Таким образом, один Markdown-файл становится полной историей выполнения конкретного задания.

## 12. Общие ограничения для ИИ-агента

Агент обязан соблюдать следующие правила:

1. Не выбирать задания самостоятельно из `backlog`.
2. Не начинать выполнение заданий из `done`, `failed` или `questions`.
3. Не изменять первоначальные требования пользователя без согласования.
4. Не скрывать ошибки и проваленные тесты.
5. Не удалять существующие тесты ради получения успешного результата.
6. Не выполнять дополнительные несогласованные задачи.
7. Не переносить задание в `done`, если обязательные проверки не пройдены или не выполнены.
8. Не считать непроведённые тесты успешно пройденными.
9. Не удалять файлы заданий после завершения работы.
10. Всегда дополнять файл задания отчётом.
11. Не выполнять коммиты и не отправлять изменения в удалённый Git-репозиторий без отдельного разрешения пользователя.
12. Не изменять содержимое других заданий, находящихся в `docs/tasks`.
13. Не исправлять автоматически ошибки, не связанные с текущим заданием.
14. Не изменять несвязанные компоненты проекта.
15. Не выдавать предположения за проверенные факты.

Если во время работы обнаруживаются посторонние проблемы, их необходимо зафиксировать в отчёте, не исправляя автоматически.
